# Consumed-token identity migration design

Status: design with executable SQLite research fixtures; the persistent store
encoding has not changed and no activation path loads these fixtures.
Related PROD_PLAN tasks: replay namespace/grace collision audit and consumed-JTI
retention through verifier leeway. This requires security/domain review before
activation. No live database, deployment or signing key is changed here.

## Observed identities

The server currently makes a namespace by concatenating audience, purpose and
transport with `;`. Absent purpose/transport become literal `default`. The JWT
crate makes a store key by concatenating namespace and JTI with `::`, or uses a
bare JTI for absent/blank namespace. The SQLite primary key stores only this
string and expiry. Consequently legacy rows cannot be uniquely decoded into
their original tuples. Escaping delimiters in new keys alone would lose the old
consumption identity and permit replay.

The volatile QUIC grace tracker is separate. It now uses a typed tuple, preserves
exact nonblank JTI bytes and absent option values, and binds issuer, verified
audience and SHA-256 of the exact normalized signed token. It contains no
persistent records to migrate. Its retained keys are domain-separated fixed-size
SHA-256 fingerprints of the typed identity, including a separate actual request
verification-scope fingerprint. The cache has 4096 entries and immutable recorded
deadlines; capacity refusal loses grace availability, never the consumed-JTI
check. This changes grace eligibility, not consumed-JTI
storage or the sealed JWT verification response.

## Required persistent transition

1. Define a versioned canonical tuple, with explicit optional namespace and JTI
   boundaries. The server scope itself must be a versioned tuple preserving
   absence versus literal values. A namespace string generated by the new server
   cannot substitute for the old namespace projection during migration.
2. Keep an explicit legacy projection function matching every old behavior,
   including blank namespace handling, `default` option substitution and exact
   JTI bytes. Existing rows are legacy tombstones, not a source from which to
   guess canonical tuples. Ambiguous old collisions remain conservatively
   rejected while their tombstones are live.
3. Check canonical consumption and the legacy tombstone in one transaction/lock,
   then insert the canonical record atomically. Separate `check_and_insert`
   calls cannot implement this: a failed second call can leave a partial write,
   and concurrent callers can each observe a different identity as unconsumed.
   The JtiStore interface needs one explicit atomic operation. Unsupported
   third-party store implementations must fail closed, not fall back to a
   two-call compatibility implementation.
4. Freeze legacy writes at cutover and retain legacy reads until the latest
   possible old-token acceptance deadline. New canonical writes must not keep
   extending ambiguous legacy tombstones indefinitely. Continuous dual writes
   preserve the original collisions and cannot be the final implementation.
5. Prevent old binaries from consuming into an independent empty legacy table.
   A deployment runbook must quiesce old writers. SQLite also needs a durable
   schema fence: a compatibility view/triggers that reject old insert/delete
   operations, verified against the old store's actual open/create/purge/insert
   statements. A version marker alone is insufficient because old code does
   not read it. PostgreSQL, in-memory and external implementations need their
   own enforced fence or a verified stop-the-world transition.
6. Rollback must retain every canonical consumption. Returning to an old binary
   with only the original legacy rows reopens tokens consumed after cutover.
   Any supported rollback needs a conservative legacy projection of canonical
   rows and an atomic schema reversal; otherwise rollback must remain fenced.

## Expiry and historical limits

The original verifier accepted a token through `exp + leeway`, but store cleanup
used raw `exp`; SQLite also truncates to seconds. This removed consumed rows while
the same signed token remained acceptable. Newly inserted records now retain
consumption through `exp + leeway + 1 second`, with checked time overflow. Actual
in-memory and reopened SQLite tests cover the inclusive acceptance boundary.
Existing raw-exp rows are not silently rewritten; a reviewed retention/drain
transition is still needed for their history before migration.
All workers sharing a ledger must agree on a maximum acceptance/retention policy;
a later increase of leeway cannot resurrect previously deleted consumption data.

Rows already purged cannot be reconstructed from delimiter strings or spectral
estimates. A transition claiming to preserve all old-token consumption must
prove complete retained history, or impose a cutover acceptance fence on legacy
tokens (for example a reviewed signing-key rotation/retirement or a bounded
drain of the entire old-token lifetime). Optional/missing `iat` cannot be assumed
to identify issuance before cutover. Existing trusted audit history may help,
but synthetic/inferred events cannot replace consumed-token records.

## Acceptance evidence required

- Independently constructed delimiter/sentinel/bare-JTI collisions stay blocked
  if a corresponding legacy tombstone exists; distinct clean canonical tuples
  work independently after legacy retention ends.
- Reopen a real WAL SQLite database containing old consumed rows; verify they
  remain rejected under the new verifier and under concurrent workers.
- Crash/retry between transaction stages, expired/no-expiry records, duplicate
  canonical writes and unsupported external stores all fail safely.
- Run the old implementation against the fenced schema: startup or writes fail
  explicitly, never create a fresh accepting store.
- Prove rollback and leeway/precision retention at acceptance boundaries.
- Review API compatibility, external JtiStore implementations, database backup
  and key/worker cutover rules before release. No advisory suppression or ledger
  deletion constitutes migration evidence.

## Actual legacy-store fence evidence

`crates/jwt/tests/replay_schema_fence.rs` tests the real current SqliteJtiStore
against temporary WAL databases. It includes test-only `replay_fence.sql` and
`replay_rollback.sql`; neither file is a production migration or loaded by the
verifier. The fixture renames the old table to retained legacy tombstones,
keeps its existing global expiry index and exposes a compatibility `jti` view
whose insert/delete/update triggers abort legacy writes. A canonical fixture
table holds explicit legacy projections for rollback evidence, not guessed
tuples decoded from historical delimiter keys.

Observed behavior is stronger than a version-marker fence: `user_version=2`
alone does not stop the actual old implementation from consuming new JTIs.
After the view fence, an already-open old store fails inserts in the trigger;
its expired cleanup fails before deleting any tombstone. Reopening the actual
store fails at `CREATE INDEX` with `views may not be indexed`, even though the
old index still exists. A prior assumption that IF NOT EXISTS would permit
startup was contradicted by the real test and corrected. No fresh `jti` table
appears. Server state construction currently propagates SqliteJtiStore::open
errors rather than falling back (`crates/server/src/state.rs`).

Six controls also verify that an aborted IMMEDIATE transaction restores the old
schema and consumption, and that conservative rollback atomically projects
post-cutover fixture rows before restoring the table. On projection collisions,
NULL expiry remains permanent and finite expiries use the maximum; canonical
rows are retained. Reopened legacy stores still reject projected consumed JTIs.
This is transaction-failure/retry evidence, not a process-kill/power-loss test.

```powershell
cargo test -p aunsorm-jwt --all-features --test replay_schema_fence --locked -j1
```

Still required: an actual versioned canonical identity/atomic consume API,
concurrent new-writer/crash campaigns, maximum retention policy, preserved or
drained legacy history, external/in-memory fences, rollout/backup authorization
and security review. Fixture canonical rows are inserted explicitly by the
test, not by a new verifier; these controls do not prove a complete migration.
